# QuickTranslate 迭代计划

制定于 2026-11-12，基线为 v1.6.2 正式版加上尚未合并的 [PR #1](https://github.com/MYPoems/QuickTranslate/pull/1)（Office 取词修复与 5 项代码审查修复）。

本计划把后续工作排成四个版本和一组持续进行的工程项。每个条目写明要改什么、主要涉及哪些文件、怎样算完成。工作量用 S / M / L 表示相对大小（S 约半天以内，M 约一到三天，L 需要拆分成多个提交并单独验收），不是日期承诺。版本号是暂定的。

## 1. 现状与依据

**已经具备**：划词与截图翻译、云端和两种离线 OCR、云端和离线朗读、历史、生词本、应用内更新与升级备份。凭据只进 Windows 凭据管理器，CSP 严格，更新包校验来源、版本和签名。

**这份计划依据的事实**：

| 来源 | 结论 |
| --- | --- |
| PR #1 | 取词根因已修复，但只用仓库外的测试驱动验证过，未经完整应用构建验收 |
| 代码审查 | 10 项发现，5 项已修，5 项未处理（见 1.6.3） |
| 源码 | 翻译为一次性返回，无流式；语言方向只分中英；翻译、OCR、朗读各只有一个 Key |
| 源码 | `AppError::Settings` 对用户统一显示“设置保存失败”，后端写好的具体原因（如“划词翻译与 OCR 快捷键不能相同”“远程 Provider 必须使用 HTTPS”）到不了界面 |
| 源码 | 悬浮窗空状态写死“选择文字后按 Alt + Q”，不随自定义快捷键变化 |
| 源码 | 悬浮窗固定状态只存在内存里，重启后丢失 |
| 源码 | 生词本每日复习上限按 UTC 日统计，在东八区是每天早上 8 点重置 |
| 源码 | 历史与翻译缓存是同一张表，上限 1000 条；“清空历史与缓存”会连收藏一起删除 |
| 界面截图 | 悬浮窗缩到最小尺寸（360 × 180）时只看得到原文，译文在可视区域之外 |
| 界面截图 | 设置页中英文标签混用（Provider、Base URL、Model 与中文并列），快捷键是纯文本输入框 |
| 构建产物 | 本地 OCR 相关的三个文件合计约 49 MB，已按窗口懒加载，悬浮窗自身的脚本只有约 11 KB，启动体积不是当前的问题 |
| 源码 | 前端多处单行超长：`vocabulary.ts` 127 行里 42 行超过 200 字符，最长 893；`popup.ts` 23 行超长 |

## 2. 约束

沿用 `CLAUDE.md` 的边界，任何条目都不得突破：

- 保持小、快、事件驱动。不引入前端框架、长期轮询、全局键盘钩子或常驻服务。
- 敏感操作、持久状态和校验留在 Rust，不信任前端传来的状态或时间。
- 不自动下载插件、不静默切换引擎、不为离线模式上传截图；云端失败不悄悄降级。
- Key、翻译原文、截图、词库不进 Git、日志、公开 Release 或测试夹具。
- 设置 Schema 升级要保留旧版快照，未来 Schema 不能被旧程序无声覆盖。
- 改源码、构建、覆盖安装、推送、公开发布是不同的授权。

| 版本 | 主题 | 一句话目标 |
| --- | --- | --- |
| 1.6.3 | 收尾与可见的错误 | 把取词修复真正交到用户手里，清掉已知缺陷 |

## 5. v1.7.0：服务配置与设置页

**目标**：解决“一个 Key 对多个服务商”的根本问题，同时把设置页从“能填”做到“不容易填错”。

### 5.1 Key 与服务地址绑定（M）

已确定不做多档可切换的配置档，只把 Key 与地址绑定。

- 翻译、云端 OCR、云端朗读的 Key 都按服务地址（协议、主机、端口）分别保存；发请求时只取与当前地址对应的那一个。
- 换到另一个地址时，那个地址没有 Key 就显示“未配置”，原地址的 Key 保留，换回来不用重新输入。
- 旧版保存的单个 Key 在首次启动时归属到当时的地址，只迁移一次；旧凭据条目保留，降级回旧版仍可使用。
- 翻译缓存键加入服务地址，解决“换端点后命中旧结果”。升级后旧缓存不再命中，历史记录保留。
- 撤掉“换地址必须重填或删除 Key”的限制。
- 不改设置 Schema。
- 涉及：`security/secret_store.rs`、`commands/settings.rs`、`commands/speech.rs`、`app.rs`、`translation/service.rs`、`storage/cache.rs`、`qa.rs`。
- 完成标准：从 1.6.x 升级后不需要重新输入 Key 就能翻译；在两个服务商之间来回切换不需要重新输入任何一方的 Key；任何情况下一个地址的 Key 都不会发到另一个地址；迁移有单元测试覆盖。

- 现状：默认配置指向 OpenAI 且没有 Key，新用户第一次按快捷键只会看到“请先在设置中配置 API Key”，设置入口只在托盘菜单里。

- 完成标准：全新安装的用户不查文档，三步内完成第一次翻译。

## 6. v1.8.0：悬浮窗与流式翻译

**目标**：缩短“按下快捷键到看见译文”的等待，让悬浮窗在各种尺寸和出错情况下都好用。

### 6.1 流式输出（L）

- Provider 以流式方式请求，后端按 `request_id` 推送增量事件，悬浮窗逐段追加。
- 新请求到来、关闭悬浮窗、重新翻译都要中止旧的流，迟到的增量不得出现在新界面上。
- 完成后才写缓存；中途失败不缓存半截结果。
- 单词释义仍走一次性的结构化请求，因为需要完整 JSON。
- 超时从“30 秒总时长”改为“首段到达超时”加“段间空闲超时”，长文本不再被总时长截断。
- 服务端不支持流式时自动退回一次性请求。
- 涉及：`providers/openai_compatible.rs`、`translation/service.rs`、`app.rs`、`popup.ts`、`types.ts`。
- 完成标准：约 500 字的段落，第一段译文出现时间明显早于现在的整段返回（发布前实测并记录数值）；连续快速触发三次，界面只显示最后一次的结果。

### 7.4 取词兜底（评估）

对不响应 `Ctrl+C` 的程序（终端、部分 PDF 阅读器）评估 UI Automation 只读取词。只在通用链路失败时启用，不启动其他程序、不读取整份文档、不绕过禁止复制的策略。先用测试驱动量化收益，再决定是否实现。

**评估结果（2026-11-12）：暂不实现。** 用合成文档探测焦点控件的 UI Automation 接口（只记录长度和耗时）：

| 程序 | 结果 |
| --- | --- |
| 记事本 | 能读到选区（60 字符）；首次调用 281 ms，之后约 8 ms |
| Word | 焦点元素是不带文本接口的窗格，读不到选区；要拿到选区得遍历文档子树或改用 Office COM |
| Excel | 焦点单元格的文本接口返回空选区；值接口只有活动单元格，选中多格时拿不到其余单元格 |

结论：UI Automation 不能直接顶替剪贴板链路。它在记事本这类本来就能复制的程序上可用，在 Office 上反而拿不到或只拿到一部分，首次调用的耗时也比现在整个取词过程长。真正不响应 `Ctrl+C` 的程序（终端、PDF 阅读器）这次没有测，是否有收益仍未知；等有具体的失败程序再按程序单独评估，不做通用兜底。现在无选区时悬浮窗已提供手动输入，可以粘贴后翻译。

## 10. 每个版本的发布门槛

1. `npm run check`、`npm test`、`npm run build`、`cargo fmt --check`、`cargo clippy -D warnings`、`cargo test` 全部通过，以 CI 为准。
2. 涉及原生行为的改动有真机验收记录，写明构建版本、测试的程序和未覆盖的情形。
3. 涉及 Schema 或数据库迁移的版本，从上一个正式版做一次完整的应用内升级，并核对设置、窗口尺寸、历史、词库、插件都保留。
4. 发布说明区分“改了什么”“怎么验证的”“还没验证什么”。
